# 02 · 代码分支与提交规范

> 目标：四个人 + 若干 AI 会话同时改代码时，能看懂每条改动属于哪个里程碑、能不能合并。

## 一、分支

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 可演示基线 | 只能从 `dev` 合并；合并前必须能按 README 起来 |
| `dev` | 集成分支 | 各功能分支合入目标 |
| `feat/mN-<主题>` | 里程碑功能 | 例：`feat/m2-live-canvas` |
| `fix/<主题>` | 缺陷修复 | 例：`fix/ws-reconnect-loop` |
| `docs/<主题>` | 纯文档 | 不影响代码 |

- 功能分支生命周期不超过 2 周，超期先拆小或回收。
- 里程碑完成时打 tag：`m1`、`m2`…；演示交付打 `demo-v1`。

## 二、提交

### 信息格式

```text
<类型>(<范围>): <一句话>

<可选正文：为什么改、影响什么>

里程碑: M2
```

| 类型 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修缺陷 |
| `docs` | 只改文档 |
| `refactor` | 重构，不改行为 |
| `perf` | 性能 |
| `test` | 测试 |
| `chore` | 构建、依赖、脚本 |

`范围` 用阶段名：`frontend`、`backend`、`ai`、`simulator`、`alerting`、`notes`、`deploy`。

### 提交纪律

- 一次提交只做一件事；混了格式化与逻辑改动时拆开。
- 不提交注释掉的死代码、调试 `console.log`、临时脚本。
- 不提交 `.env`、密钥、数据库文件、`artifacts/` 下的证据。
- 契约变更的提交必须同时改 [[01-项目调研规划与开发建设记录/01-第一版-演示平台/03-架构设计/02-接口契约]]，否则不合入。

## 三、代码风格

| 侧 | 约定 |
| --- | --- |
| 前端 | ESLint + Prettier；组件 `PascalCase.vue`，组合式函数 `useXxx.ts`，类型放 `types/`；禁止在模板里写复杂表达式 |
| 后端 | 分层 `controller / service / mapper / domain`；DTO 与实体分离；异常统一抛业务异常，由全局处理器转包络；禁止 controller 里写 SQL |
| 推理 | 类型标注齐全；`Detector` 抽象基类，实现类只做推理不做业务；配置从环境变量读 |
| 通用 | 函数单一职责；魔法数字进配置或常量；每个 `TODO` 注明里程碑与负责人 |

## 四、评审

- 每个功能分支合并前至少 1 人 review，**作者不能自审**。
- review 关注：契约一致性、边界条件、错误处理、是否有占位标记缺失。
- 评审意见分「必须改」与「建议」；必须改未清不合入。

## 五、依赖管理

- 新增依赖须说明用途与体积影响，前端优先按需引入（ECharts、Element Plus）。
- 锁文件（`package-lock.json`、`pom.xml` 版本、`requirements.txt`）必须提交，且固定版本。
- 不引入来源不明的包；算法侧不引入未经许可的权重文件。
