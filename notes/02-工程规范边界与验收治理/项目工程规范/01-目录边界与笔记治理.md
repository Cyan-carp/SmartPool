# 01 · 目录边界与笔记治理

> 本卷维护目录、Vault 边界、文件放置与笔记排版。入口见 [[02-工程规范边界与验收治理/项目工程规范/00-索引·项目工程规范]]。

## 一、一句话定位

一个仓库、代码按阶段切分；**笔记与代码物理隔离**：正式笔记全部进 `notes/`，代码进 `stages/`，编排脚本进 `deploy/`，大型证据留在 Vault 外的 `artifacts/`。

## 二、维护规则

- **单一声明**：同一条约定只在本目录声明一次；阶段内具体命令以各阶段 README 为唯一入口。
- **变更需确认**：新增长期规则先提建议（拟改章节、理由、影响），确认后写入；排障经验不自动升格。
- **增补先查重**：能并入原卷的并入，拿不准放最贴近主题的卷末并说明理由。
- **现行与历史分开**：现行条款替换过时要求；带日期的批次与失败证据原样保留。
- **不写入本卷的内容**：一次性操作决定、临时排障结论、阶段内实现细节（分别归阶段页、问题记录页、部署日志）。

## 三、项目结构总览

```text
SmartPool/
├── README.md                       # 仓库级导航
├── AGENTS.md                       # AI 协作约定
├── SKILL.md                        # Obsidian 协作说明
├── notes/                          # ★ 唯一 Obsidian Vault
│   ├── 00-项目笔记总入口.md
│   ├── 00-项目目录导航.md
│   ├── 00-当前系统状态.md
│   ├── 01-项目调研规划与开发建设记录/
│   ├── 02-工程规范边界与验收治理/
│   ├── 03-系统使用与运维手册/
│   ├── 04-部署发布与变更记录/
│   └── 05-代码工作区导航与链接映射/
├── stages/                         # ★ 阶段源码与各自 README
├── deploy/                         # ★ 编排、Nginx、演示环境脚本
├── tools/note-governance/          # 笔记校验
├── shared-memory/                  # 跨对话协作记忆（Vault 外）
├── artifacts/                      # Git 忽略的运行证据
└── backups/                        # 备份登记（包体不入库）
```

### Vault 边界（强制）

- Obsidian **只打开** `SmartPool/notes/`，不得把仓库根作为 Vault。
- `stages/`、`deploy/`、`tools/`、`artifacts/` 均在 Vault 外；笔记通过 [[05-代码工作区导航与链接映射/00-索引·代码工作区导航]] 的代理页访问代码。
- 根 README 与阶段 README 属于代码侧导航，不复制进 Vault；设计、验收与日志只在 `notes/` 维护。
- 大型证据、原始日志、私有配置不进 Vault，也不进 Git。
- 笔记结构调整后运行 `python tools/note-governance/check_notes.py`，通过才算完成。

### 跨对话共享记忆

- `shared-memory/` 用于多个 AI 会话之间交接上下文，**不属于**正式笔记，也不能替代设计文档、测试证据或验收结论。
- `project-memory.md` 只保存跨对话长期有效且已确认的事实；临时判断与进度留在 `conversations/<日期>/`。
- 禁止写入密码、令牌、密钥、完整隐私数据与未脱敏日志。

## 四、文件放置规则

| 类型 | 归属 |
| --- | --- |
| 需求、选型、架构、契约、数据模型 | `notes/01-…/01-第一版-演示平台/01～03-*` |
| 里程碑方案 / 测试与交付 / 问题记录 / 交接 | `notes/01-…/05-功能开发与阶段交付/NN-Sxx主题/` |
| 测试脚本说明、合成数据口径、资产台账 | `notes/01-…/06-测试数据与测试资产/` |
| 工程规范、验收清单、产物说明 | `notes/02-工程规范边界与验收治理/` |
| 使用与运维手册 | `notes/03-系统使用与运维手册/` |
| 部署、备份、变更批次 | `notes/04-部署发布与变更记录/部署与运维日志/` |
| 阶段源码与脚本 | `stages/NN-<英文主题>/` |
| 编排、Nginx、演示环境 | `deploy/` |
| 私有配置与密钥 | 本机根 `.env`；不入 Git |
| 截图、日志、导出文件 | `artifacts/<阶段>/<run_id>/`（Git 忽略） |

## 五、单仓库分阶段要求

| 维度 | 约定 |
| --- | --- |
| 源码 | `stages/NN-<英文主题>/`，至少一份 `README.md`；子目录按实际依赖建，不强制齐备 |
| 索引对齐 | 阶段 README 与阶段笔记索引互相指向；根 README 维护总表 |
| 阶段边界 | 每阶段只做本阶段的事，不提前引入后续组件（M1 不做告警、M2 不做围栏） |
| 复用 | 确认复用两次以上再抽公共模块，不提前抽象 |
| 测试交付 | 每阶段必须有标题含「测试与交付」的正式笔记 |
| 问题记录 | 每阶段一份独立问题记录页，每条含现象、原因、影响、解决办法、验证结果、状态 |

## 六、笔记排版规范

### 文件骨架

1. **frontmatter** 必须含 `tags`、`status`、`scope`、`updated`；`status` ∈ `现行/历史/废弃/草稿`，`updated` 用 ISO 日期。
2. 一级标题 `# 主题`；索引用 `# 模块 · 索引`。
3. 标题下用 `>` 写「本页说明什么 + 对应哪项任务」。
4. 正文用 `## 一、二、三…` 分节。
5. 末尾「相关笔记」小节标明上下游。

### 正文元素

6. 短并列信息用表格；长句、多组数字改用列表。
7. 关键提醒、设计决策的「为什么」用 `>` 引用框。
8. 架构图用 Mermaid 或等宽 ASCII 代码块。

### 链接与术语

9. 同目录用短链 `[[00-索引·xx]]`；跨目录用全路径双链，避免同名歧义。
10. 功能编号（FR/NFR）与里程碑编号（M1–M6、S01–S06）只在一处分配，其它页面只引用。

### 反堆叠写法

> 笔记出现「整段灰墙、表格过宽、代码连片」时，按下列规则重排，语义与路径一律不改。

- **长段 → 列表**：一句话串了多个并列事实时，拆成 2–4 条，每条只讲一件事。
- **宽表格 → 加粗小标题 + 列表**：某格塞进长句或多组数字时，放弃表格。
- **代码块 → 步骤化**：每段前加 `#### 步骤 N · 动词短语`，关键注释用引用框。
- **边界与结论 → 引用框**：「不能只凭 X 判定通过」这类限定结论单独放引用框。
- **分组**：超过 6 条的无序列表，按主题拆组并加粗小标题。

### 状态只写一处（硬性）

- 现行状态只在 [[00-当前系统状态]] 维护：阶段、口径、已实现能力、已知限制。其它页面只写一句 `当前状态见 [[00-当前系统状态]]`。
- 入口文档（README、手册、验收清单、各阶段 README）顶部不得按日期堆叠进度批次。
- 可以留在原页的「状态」只有两类：一次性验收里程碑，以及该页自身的维护说明。

## 七、移动与改名（强制）

移动、改名、合并任何笔记或文件夹时，**同一批**完成：

1. 已跟踪文件用 `git mv` 保留历史。
2. 全库重写指向旧路径的 Markdown 链接与双链（含 `stages/` 下的 README）。
3. 同步根 README 目录、所属文件夹索引、[[00-项目目录导航]] 与本卷的目录树。
4. 运行 `check_notes.py`，确认旧路径零残留。

> 只搬文件不改索引，视同任务未完成。
