# 总体架构与数据流

> 描述演示版的进程边界、模块职责与一次告警的完整路径。部署细节见 [[02-工程规范边界与验收治理/项目工程规范/06-部署与服务器上传规范]]。

## 一、进程与边界

```text
┌──────────────────────────────────────────────────────────────────┐
│ 浏览器（Vue 3 控制台）                                            │
│  监控大屏 · 告警中心 · 电子围栏 · 看板 · 设备 · 配置 · 演示控制台   │
└───────────────▲──────────────────────────┬───────────────────────┘
        WS 推送  │                          │ REST（Axios）
┌───────────────┴──────────────────────────▼───────────────────────┐
│ Spring Boot 后端（stages/02-backend，:8080）                      │
│  鉴权 · 泳池/区域 · 告警 · 事件 · 设备 · 水质 · 调度 · 统计 · 审计  │
│        │                    │                    │               │
│     MySQL 8.0           Redis 7            告警分发(05-alerting)  │
└────────▲─────────────────────────────────────────────────────────┘
         │ 内部 REST（检测结果上报 + 状态回调）
┌────────┴─────────────────────────────────────────────────────────┐
│ Python 推理服务（stages/03-ai-service，:8000）                    │
│  Detector(mock|mamba-yolo) · Tracker(占位) · RiskScorer · 剧本引擎 │
└────────▲─────────────────────────────────────────────────────────┘
         │ 合成帧元数据 / 剧本指令
┌────────┴─────────────────────────────────────────────────────────┐
│ 模拟数据源（stages/01-simulator，:8010）                          │
│  游客生成 · 游动轨迹 · 手环生理 · 水质漂移 · 摄像头健康            │
└──────────────────────────────────────────────────────────────────┘
```

> **为什么推理是独立进程**：模型将来要换语言栈、换 GPU 机器、可能要独立扩缩容。把检测/跟踪/风险分放在 Python 侧，后端只消费结构化结果，避免 Java 侧再写一遍模型逻辑。

## 二、模块职责

| 模块 | 职责 | 不属于它的事 |
| --- | --- | --- |
| 模拟数据源 | 生成游客、位置、姿态、手环、水质、设备状态与剧本事件 | 不判定风险、不写业务库 |
| 推理服务 | 帧级检测（占位）、`track_id` 分配（占位）、窗口内风险打分 | 不落业务库、不发通知、不做权限 |
| 后端 | 唯一业务事实源：区域、告警生命周期、处置、审计、统计 | 不做图像处理、不做前端渲染逻辑 |
| 告警分发 | 按级别与订阅渠道外发（站内 / Webhook / 飞书） | 不改告警状态（只记投递结果） |
| 前端 | 呈现、交互、本地渲染合成画面与叠加层 | 不做风险判定、不缓存业务真相 |

## 三、一次强告警的完整路径

1. **t0**：模拟数据源按剧本让 7 号游客停止划水，头部沉入水下（姿态 `underwater_still`）。
2. **t0+1s**：推理服务收到帧元数据，`MockDetector` 按剧本输出该目标的框与姿态；`RiskScorer` 累计「头部未出水时长」与静止程度，风险分从 0.2 抬到 0.86。
3. **t0+2s**：风险分越过强告警阈值，推理服务 `POST /internal/risk-events` 上报事件（含 `poolId`、`trackId`、`riskScore`、`evidence`）。
4. **t0+2s**：后端写入 `risk_event`，按「同泳池 + 同 track + 60s 窗口」去重合并生成/升级 `alert`，同时手环数据交叉校验（心率 128 平稳 → 标记 `uncertain`，避免立刻强告警）。
5. **t0+3s**：后端经 WebSocket 广播 `alert.created`；前端大屏将该目标描红、弹出强告警卡、播报提示音。
6. **处置**：救生员点「已确认」→ `POST /api/v1/alerts/{id}/ack` → 状态 `ACKED`；现场处置后「解除」并填写结论。
7. **归档**：后端把处置时间线写入 `alert_action`，并在 `event_clip` 中冻结该时间窗的轨迹与风险曲线，供事件回溯回放。

## 四、关键设计决策

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 检测结果不逐帧落库，只落风险事件与片段 | 逐帧存储爆炸，演示与真实都不需要 | 无法做帧级回放；回溯依赖片段缓存 |
| 风险判定在推理侧，告警生命周期在后端 | 判定依赖时序窗口，后端不应持有模型上下文 | 两侧要维护阈值口径一致 |
| 前端坐标一律归一化（0–1） | 与分辨率解耦，合成画面与真实画面共用叠加层 | 真实标定需额外米制换算层 |
| WebSocket 只做推送，查询走 REST | 简化服务端状态，断线可重连补快照 | 前端需处理「快照 + 增量」拼接 |
| 演示时钟可倍速 | 讲解时不必等 30 秒真实时长 | 所有时间戳必须来自服务端时钟，不能前端自造 |

## 五、状态与失败处理

| 故障 | 表现 | 系统行为 |
| --- | --- | --- |
| 推理服务不可用 | 无新检测帧 | 大屏置灰 + 顶部「分析中断」条；已有告警不自动解除 |
| 模拟数据源断开 | 人数不再变化 | 后端按最后上报时间标记「数据延迟」，超过 30s 标记「离线」 |
| WebSocket 断开 | 前端收到 `onclose` | 指数退避重连（1s/2s/5s/10s），重连后先拉 `/api/v1/live/snapshot` |
| MySQL 不可用 | 写告警失败 | 告警进 Redis 待写队列并保留 10 分钟，恢复后补写；期间前端显示「写入延迟」 |
