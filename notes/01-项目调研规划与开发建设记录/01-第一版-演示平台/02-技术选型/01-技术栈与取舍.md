# 技术栈与取舍

> 与申报书对齐为主，演示可行性优先。申报书列出的重型组件拆成「演示版启用」与「研究目标」两栏，避免口径混淆。

## 一、总表

| 层 | 演示版选型 | 理由 | 研究目标（申报书） |
| --- | --- | --- | --- |
| 前端框架 | Vue 3.4 + Vite 5 + TypeScript 5 | 与申报书一致，团队已有基础；Vite 启动快，适合演示迭代 | 同 |
| UI 组件 | Element Plus | 监控面板、表格、弹窗、权限指令开箱可用 | 同 |
| 图表 | ECharts 5 + vue-echarts | 热力图、折线、仪表盘齐全；按需引入控制体积 | 同 |
| 状态管理 | Pinia | Composition API 友好，模块拆分清晰 | 同 |
| 请求 | Axios + 拦截器 | 统一错误提示、token 注入、超时重试 | 同 |
| 实时通道 | WebSocket（原生 + 自封装重连） | 双向低延迟；断线重连 + 快照补拉 | 同 |
| 后端框架 | Spring Boot 3.2 + MyBatis-Plus | 与申报书一致；单服务即可覆盖演示 | + Spring Cloud 微服务 |
| 鉴权 | Spring Security + JWT | 三角色 RBAC，演示足够 | 同 |
| 数据库 | MySQL 8.0 | 关系型结构清晰，便于审计与回溯 | 同 |
| 缓存 | Redis 7（Lettuce） | 实时快照、告警队列、限流、在线端计数 | 同 |
| 消息 | 演示版**不引入 Kafka**，用 Spring 事件 + Redis List | 单机演示无跨服务解耦需求，省一个中间件 | Kafka 事件解耦 |
| 推理服务 | Python 3.11 + FastAPI + Pydantic + OpenCV | 轻量、契约清晰、异步友好；与将来模型代码同语言 | Mamba-YOLO + DeepSORT + Temporal Transformer |
| 模型运行时 | `Detector` 接口 + `MockDetector` | YOLO 空置；剧本驱动输出检测框 | selective_scan CUDA、真实权重 |
| 视频处理 | 演示版**不做** FFmpeg 转码，前端 Canvas 合成画面 | 避免演示环境依赖编解码与带宽 | FFmpeg + OpenCV 抽帧/增强 |
| 部署 | Docker Compose + Nginx | 一台机器起全套；Nginx 统一入口与 WS 升级 | Docker + K8S |
| 测试 | 前端 Vitest，后端 JUnit 5 + MockMvc，推理 pytest | 覆盖契约与关键判定逻辑 | 同 |

## 二、关键取舍说明

### 为什么模型先用占位

- 权重与训练环境尚未就绪，业务侧不应被阻塞。
- 占位实现能验证**契约、时序、告警逻辑与界面**，这些是演示的主体。
- 切换成本被压到一个提供者类与一个配置项（`AI_DETECTOR_PROVIDER`），符合 [[02-工程规范边界与验收治理/项目工程规范/05-演示数据与模型占位边界]]。

### 为什么不用 Spring Cloud / Kafka / K8S

- 演示是单机单进程场景，拆分只会增加启动时间与排障面。
- 申报书中的微服务与消息队列属于**架构演进目标**，将来拆分的边界已在 [[01-项目调研规划与开发建设记录/01-第一版-演示平台/03-架构设计/01-总体架构与数据流]] 预留（推理与告警已独立进程），不是推倒重来。

### 为什么画面用 Canvas 合成

- 真实泳池画面涉及隐私与版权，仓库不能携带。
- 合成画面能精确控制「正常游泳 → 静止下沉 → 风险升级」的演示节奏，比真实录像更可控。
- 后续接真实流时，把 Canvas 层替换为 `<video>`/HLS 播放器，检测框叠加层与坐标系不变。
